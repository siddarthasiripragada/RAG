§ 01 — RAG ARCHITECTURE

RAG Generations & Patterns

RAG has evolved through four distinct generations. Each solves failure modes of the previous. Knowing the evolution signals deep domain understanding in an interview.

🌿 Naive RAG
Index → Retrieve → Generate. No query refinement, no re-ranking. Suffers from poor retrieval precision, hallucination when context is noisy, and semantic mismatch between question style and document style.
⚙️ Advanced RAG
Pre-retrieval (query transform) + Retrieval + Post-retrieval (re-rank, filter). Addresses precision and mismatch. Still a fixed linear pipeline — every query takes the same path regardless of complexity.
🔧 Modular RAG
Pluggable components — swap any module independently. Multi-modal, multi-hop, hybrid retrieval, custom routing. Flexible architecture but requires significant orchestration engineering.
🤖 Agentic RAG
LLM decides when to retrieve, what to retrieve, and whether to trust the result. Self-RAG, CRAG, Adaptive RAG, LangGraph. Highest quality, highest latency, highest engineering complexity.
RAG vs Fine-Tuning vs Prompting — The Full Decision Tree

Use Prompting alone when the answer exists within the model training data, the query is simple, and latency is critical. Example: "Explain what JWT is."

Use RAG when knowledge is external to the model, updates frequently, must be auditable or citable, or spans many private documents. Example: "What does our compliance policy say about data retention in Canada?"

Use Fine-Tuning when you need to change the model style, tone, or output format — or bake in domain-specific reasoning patterns that are stable and don't change. Example: Medical note generation requiring specific clinical SOAP format.

Use RAG + Fine-Tuning together when the model needs domain vocabulary to understand retrieved content AND retrieval of external docs is required. Fine-tune for format and reasoning style; RAG for live knowledge injection.

Never RAG when: (1) Knowledge base is fewer than a few hundred documents — fine-tune or prompt-engineer instead. (2) Exact SQL or structured data lookup is needed — RAG adds noise to tabular queries. (3) The answer is a real-time metric — use tool calls and live APIs.

Interview Q&A — RAG Foundations
►What are the key failure modes of Naive RAG and how does each RAG generation address them?
Senior

Naive RAG has three compounding failure modes. Retrieval precision failure: Fixed-size chunks break semantic units at arbitrary token boundaries. A retrieved chunk may contain the right keyword but the wrong context — the sentence that answers the question got split off into a different chunk. Advanced RAG fixes this with parent-child chunking (retrieve precise child, return larger parent for context) and re-ranking (cross-encoder filters low-quality chunks before generation).

Query-document mismatch: User queries are questions; indexed documents are declarative statements. "What are the side effects?" versus "Common adverse reactions include..." The semantic distance causes poor ANN retrieval even when the relevant document exists. Advanced RAG fixes this with query transformation — HyDE generates a hypothetical answer in document-style before embedding, bridging the representation gap.

Context noise degrading generation: All retrieved chunks go to the LLM regardless of relevance. Irrelevant chunks dilute attention and cause hallucination. Re-ranking solves this by culling low-relevance chunks before the generation call. Modular RAG goes further by making the pipeline adaptive — some queries skip retrieval entirely, others use multi-hop. Agentic RAG gives the model agency to self-evaluate retrieved docs and retry with different queries.

►When would you explicitly recommend against RAG for a problem that seems to need it?
Principal

Four concrete cases where RAG is the wrong tool despite the apparent need for external knowledge lookup:

1. Small, stable knowledge base (<500 documents, rarely updated): Fine-tuning or system-prompt injection is cheaper, faster, and more reliable. RAG overhead — indexing infrastructure, retrieval latency, context management — isn't justified when you could stuff the entire knowledge base into a system prompt once.

2. Structured data queries: If the answer requires aggregation, JOIN, or filtering across a database (revenue by region, top-10 customers), use Text-to-SQL or function calling. RAG loses all relational structure in chunking. You cannot reliably reconstruct a SUM(revenue) from chunked document snippets.

3. Real-time data: If the answer must be seconds-fresh (stock prices, live API status, flight tracker), a vector index is too slow to keep current. Tool calls with live APIs are the correct architecture. RAG with a stale index confidently returns outdated information.

4. Zero-tolerance precision requirements: In some regulated environments, the system must produce the exact authoritative document with zero stochastic error — no retrieval misses allowed. RAG's probabilistic retrieval is architecturally incompatible. Use deterministic document lookup (exact citation ID) plus LLM for formatting, not RAG for retrieval.

The diagnostic signal: when a retrieval miss is catastrophic with no graceful degradation path, RAG introduces unacceptable risk. RAG is powerful precisely because it is probabilistic — that same property is its liability in zero-tolerance environments.

Interview Q&A — Chunking
►How do you determine optimal chunk size for a given domain and document type?
Senior

Chunk size optimization is a function of four interacting variables: query length, embedding model context window, document structure, and generation context budget.

Query-chunk length matching: Chunks and queries should be semantically similar in length. A 10-word query produces an embedding that matches best to a 100–300 token chunk. If users ask short, specific questions, use smaller chunks. If queries are paragraph-length analytical questions, use larger chunks.

Embedding model limits: text-embedding-3-large supports 8,191 tokens, but embedding quality plateaus and degrades beyond ~512 tokens for most tasks. Larger chunks dilute the embedding — too much content in one vector means it represents everything and nothing specifically. Never exceed roughly 60% of the model context window per chunk.

Empirical grid search: Start with 256/512 tokens at 10% overlap. Run your golden evaluation set. Measure Context Precision and Context Recall (RAGAS). Vary chunk size across [128, 256, 512, 1024] and overlap across [0%, 10%, 20%]. Choose the point of diminishing returns. In my experience, 256–512 tokens is optimal for 80% of enterprise document Q&A use cases.

Diagnostic signal: low faithfulness + high context precision → chunks too small (insufficient generation context). Low context precision → chunks too large (too much noise per chunk).
►Explain parent-child chunking in detail. When does it outperform standard fixed-size?
Principal

Parent-child chunking decouples the retrieval unit from the generation unit. You index small child chunks (128–256 tokens) into the vector store — focused embeddings match specific queries with high precision. But you store pointers to their larger parent chunks (512–1024 tokens or full sections). When a child chunk is retrieved, you return its parent chunk to the LLM for generation.

This solves the fundamental RAG tension: smaller chunks give precise retrieval but insufficient generation context; larger chunks give rich context but diluted embeddings that retrieve poorly. Parent-child delivers both — child precision for retrieval, parent richness for generation.

Implementation: Assign each parent chunk a UUID. Store parent_id as metadata in each child embedding. After vector retrieval, deduplicate by parent_id (multiple children may point to the same parent), then fetch parent texts from a document store (S3, Postgres blob, or Snowflake). The vector store holds child embeddings; a separate store holds parent text.

When it clearly outperforms: (1) Legal/compliance documents where the answer is one specific clause but understanding requires the surrounding section context. (2) Technical documentation where queries are specific ("what parameters does this function take?") but answers need surrounding method documentation. (3) Any domain where the relevant sentence is nested inside a broader narrative that gives it meaning.

When the complexity isn't justified: FAQ sheets, recipe databases, or any corpus where each unit is truly independent. Add parent-child only when retrieval precision AND generation context are both measurably insufficient with standard chunking.

►What is late chunking and how does it address the lost-context problem in standard chunking?
Architect

Standard chunking embeds each chunk independently. A chunk containing "it was rejected due to Article 22" produces a poor embedding because "it" has no referent — the antecedent lives in a previous chunk. This lost-context problem degrades retrieval quality for any document with significant cross-references, pronouns, or defined terms used throughout.

Late chunking inverts the process. A long-context embedding model (jina-embeddings-v3, nomic-embed-text with 8K context) first encodes the entire document in one forward pass, producing contextual token embeddings informed by full-document attention. You then aggregate (mean pool) these token embeddings over your desired chunk windows. Each chunk's embedding carries full document context — "it" is resolved, defined terms are understood, cross-references are represented.

When the cost is justified: Technical documentation with heavy cross-references and forward references; legal documents where defined terms appear in one place and are used throughout; code documentation where function names defined in one module are referenced everywhere. The retrieval quality improvement for these document types can be 8–15% Context Recall improvement over standard chunking.

The cost: You must run the full document through the embedding model for every chunk — indexing compute scales O(n_chunks × doc_length) rather than O(n_chunks). For a 1M document corpus, this can be 5–10x more expensive than fixed-size chunking at indexing time. Evaluate this tradeoff explicitly — the improvement must justify the infrastructure cost.

Interview Q&A — Embedding Models
►When do you choose sparse retrieval over dense, and when do you need both?
Senior

Pure dense retrieval excels when queries and documents are semantically related but use different vocabulary. "Adverse reactions" should retrieve chunks about "side effects." Dense embeddings capture synonymy, paraphrase, and conceptual similarity because both query and document share the same semantic encoding space.

Pure sparse (BM25): Choose when exact term matching is critical and vocabulary is domain-specific. Product codes, regulatory article numbers (APPR Section 3.2b), UUIDs, proper nouns, technical acronyms — all cases where dense embeddings may conflate similar-sounding terms or miss exact identifiers. BM25 also has zero indexing latency and is fully interpretable: you can explain exactly why a document was retrieved, which is valuable in regulated industries.

Hybrid (both): The general production default. Dense handles semantic queries; sparse handles exact match. RRF merges ranked lists without requiring score normalization. A hybrid system handles "explain the policy on passenger rebooking" (dense wins) AND "find documents mentioning regulation EC 261/2004 Article 9" (sparse wins) with a single unified retrieval call.

Rule of thumb: if your domain has significant technical vocabulary, identifiers, or proper nouns, always use hybrid. Pure dense on legal, medical, or technical domains will miss exact-match queries regularly — often the highest-stakes queries.
►How does ColBERT work and where does it fit in the retrieval stack?
Principal

ColBERT (Contextualized Late Interaction over BERT) takes a fundamentally different approach from standard bi-encoders. A standard bi-encoder encodes an entire query into one vector and a document into one vector, then computes one cosine similarity. ColBERT produces a vector per token for both query and document.

At query time, relevance is computed via MaxSim: for each query token embedding, find its maximum cosine similarity across all document token embeddings, then sum these per-token maximum similarities. This is "late interaction" — token-level attention happens at query time, not at indexing time, yet documents can still be pre-indexed (per-token embeddings stored).

Score(Q, D) = sum_i( max_j( q_i · d_j ) ) where q_i = query token i embedding, d_j = doc token j embedding

Why it matters: ColBERT bridges bi-encoders (fast, pre-indexable) and cross-encoders (slow, highest quality). Cross-encoders process query+document together in one pass — they can't pre-encode documents. ColBERT pre-indexes per-token document embeddings and achieves near-cross-encoder quality at near-bi-encoder speed for the document side.

Production role: Best as a re-ranker on top of initial dense retrieval — take top-100 from ANN, re-rank with ColBERT's MaxSim. As first-stage retrieval it requires the PLAID index (RAGatouille library) which is more complex to operate. For most production systems, Cohere Rerank or bge-reranker-v2 is simpler for re-ranking with similar quality at smaller scale.

►How would you fine-tune an embedding model for a specialized domain and what training signal is required?
Architect

Domain-specific embedding fine-tuning uses contrastive learning with positive and hard-negative pairs. The model maximizes cosine similarity for (query, relevant_doc) pairs and minimizes it for (query, hard_negative_doc) pairs — documents that look plausibly relevant but are not the correct answer.

Loss function: Multiple Negatives Ranking Loss (MNRL) / InfoNCE. For a batch of (query, positive_doc, [hard_negatives]), softmax-normalized contrastive loss. Hard negatives are critical — random negatives are too easy and produce weak, low-discrimination models. The most impactful training signal improvement is better hard negatives, not more data.

Training data sources in priority order: (1) User click/engagement logs — actual (query, accepted_answer) pairs from your system. Highest signal. (2) Synthetic pairs via LLM — use GPT-4 to generate question-answer pairs from corpus documents. Scale easily to 50K–500K pairs. (3) BM25-mined hard negatives — BM25 top-10 results that are not the true positive are near-miss hard negatives. (4) Domain adaptation from MS MARCO or NQ, fine-tuned further on your data.

Pipeline: Start from bge-large-en or e5-large-v2 as a pretrained base. Generate 50K–500K synthetic pairs. Mine hard negatives from BM25. Fine-tune 3–5 epochs with lr=2e-5. Evaluate on held-out golden set using NDCG@10. Compare to base model — if improvement is under 5%, the bottleneck is data quality, not model capacity.

Interview Q&A — Vector Databases
►Explain HNSW — how it works, its key parameters, and time/space complexity.
Principal

Hierarchical Navigable Small World (HNSW) builds a multi-layer proximity graph — think of it as a skip list applied to vector space. Each inserted vector is assigned to layers geometrically: most nodes appear only at layer 0, fewer at layer 1, fewer still at layer 2, following a geometric decay with probability m_L = 1/ln(M).

Query algorithm: Enter at the top layer through a random entry point. Greedily navigate to the ef nearest neighbors by following graph edges to closer nodes. Move to the next lower layer using the best nodes found as new entry points. Repeat until layer 0. Return top-k from layer 0 candidates. This multi-resolution traversal gives O(log n) query time.

Time: O(log n) per query. Space: O(n x M) where M = max connections per node. Rebuild: O(n x M x log n).

Key parameters:

  • M (max connections per node, default 16): Higher M = better recall, higher memory. M=16 is a good default. High-precision applications: M=32–64. Memory cost scales as M x n x 4 bytes for connection indices.
  • efConstruction (build quality, default 200): Higher value = better graph connectivity during index build, but slower indexing. Use 200–400 in production. A poorly-built graph cannot be fixed without a full rebuild — don't sacrifice this at indexing time.
  • ef (query beam width, default 64): The only parameter tunable at query time without rebuilding. Higher ef = higher recall at cost of query latency. Start at 64, increase until recall@k plateaus. This is your primary production quality lever.

vs IVFFlat: IVFFlat clusters vectors into nlist cells; queries search only the nprobe nearest cells. Faster index build, lower memory, but worse recall at equal query time. HNSW dominates for low-latency, high-recall RAG applications. IVFFlat is better for batch workloads and memory-constrained environments.

►How do you choose between Pinecone, Qdrant, and Weaviate for a production RAG system?
Principal

This is fundamentally a decision across three axes: operational model, hybrid search requirements, and performance SLA.

Choose Pinecone when: Time-to-production is the primary constraint, you have no ML platform team, and cost at scale is acceptable. Pinecone is zero-operational-overhead — no Kubernetes, no disk management, no index monitoring. Native sparse+dense hybrid. Serverless tier eliminates overprovisioning. Downside: higher per-query cost at million-query-per-day scale compared to self-hosted, and data leaves your VPC (evaluate for compliance requirements).

Choose Qdrant when: You need maximum raw query performance and can manage infrastructure (or use Qdrant Cloud). Qdrant's Rust core is consistently the fastest self-hosted vector DB in benchmark comparisons — lowest P95/P99 latency. Excellent payload-based filtering (pre-filters during ANN, not post-filter). Sparse vector support enables hybrid. Choose Qdrant when your team has platform maturity and you have sub-50ms P95 latency SLAs.

Choose Weaviate when: Native BM25+dense hybrid is a first-class requirement AND you want it with a single API call. Weaviate natively combines both modalities without requiring separate index management. Rich module ecosystem (text2vec-openai, generative modules for RAG). Go-based, good horizontal scaling. More complex to operate than Pinecone, more flexible than Azure AI Search.

My default recommendation: Qdrant (self-hosted on Kubernetes or Qdrant Cloud) if the team has infrastructure maturity. Pinecone if they don't. Azure AI Search if the organization is Azure-native — it has excellent built-in hybrid search, Azure RBAC, and AAD integration out of the box, eliminating a significant amount of security engineering.
►When is pgvector a legitimate production choice and when should you migrate to a purpose-built vector DB?
Senior

Legitimate production use cases for pgvector: Application data already lives in PostgreSQL and you need to JOIN vector search results with relational data — colocated queries without a network hop are a real advantage. Scale under 1–5M vectors with latency SLA above 100ms. Team has strong PostgreSQL expertise and no vector DB expertise. Complex filtering using arbitrary SQL predicates (pgvector post-filters on full SQL WHERE clauses, which is genuinely powerful and flexible).

When pgvector is the wrong choice: Above ~5–10M vectors, pgvector's HNSW index degrades — the index fits in memory at small scale but the PostgreSQL query planner overhead becomes the bottleneck at large scale. Hybrid search requires manual combination of pgvector results with PostgreSQL full-text search (tsvector), then manual score fusion. No native RRF. Query latency P95 requirements under 50ms at high QPS — PostgreSQL connection overhead and query planning overhead are meaningful at this scale.

The common mistake: Teams reach for pgvector because it is "one less service to manage." They ignore the operational characteristics, hit performance walls at 2–3M vectors, and face a painful migration to Qdrant or Pinecone under production load. If you know you will exceed 5M vectors within 12 months, start with Qdrant or Pinecone. pgvector is excellent up to its scale limit — the problem is when teams don't plan for that limit.

►How do you handle metadata filtering with ANN search, and how do different vector DBs approach this differently?
Principal

Metadata filtering with ANN search is one of the hardest vector database engineering challenges. ANN algorithms assume full-index search. Adding a filter (WHERE department = 'legal' AND year = 2024) fundamentally changes the search space, and naive approaches degrade severely.

Post-filtering (naive approach): Retrieve top-k via ANN ignoring filters, then filter results. Catastrophically bad for low-selectivity filters — if only 1% of vectors match the filter, you need to over-retrieve by 100x to get k valid results. At low enough selectivity, this degrades to brute-force O(n) scan.

Qdrant's approach (payload indexing): Qdrant maintains separate inverted indexes on payload (metadata) fields. At query time it computes a filtered candidate set first, then runs ANN search within that set. For high-selectivity filters (greater than ~5% of vectors match), this is fast — nearly as fast as unfiltered ANN. For very low selectivity (under 0.1% match), Qdrant automatically switches to brute-force on the filtered set. This adaptive strategy is the current state of the art.

Pinecone namespaces / Weaviate classes: Segregate vectors by a key attribute into separate namespaces or classes. Query only the relevant namespace. Avoids filter overhead entirely but requires you to predict which attributes will be filtered at design time. High-cardinality attributes (one namespace per user) can explode into thousands of namespaces — manage carefully.

Design implication: If your RAG system requires heavy filtering (multi-tenant, document type restrictions, date range queries), choose a vector DB with payload indexing (Qdrant, Weaviate) or design with namespace partitioning (Pinecone). Avoid post-filtering for high-selectivity filters — the precision collapse is severe and often invisible until production scale.

►Explain Reciprocal Rank Fusion mathematically. Why use it over linear score combination?
Principal
RRF_score(d) = sum_over_lists( 1 / (k + rank(d, list)) ) Where: d = document being scored rank() = 1-indexed position in ranked list (1 = top result) k = smoothing constant, default k = 60 sum = across all retrieval lists (dense, sparse, etc.) Example: Document ranked 1st in dense list, 3rd in sparse list (k=60): RRF = 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 = 0.03226 Document ranked 5th in both lists: RRF = 1/(60+5) + 1/(60+5) = 0.01538 + 0.01538 = 0.03077 The top-1 document in one list outscores the consistent-5th document.

Why RRF over linear combination: Linear combination requires score normalization — dense cosine scores (range -1 to 1, empirically 0.7–1.0) and BM25 scores (range 0 to ~30, heavy-tailed) have fundamentally different distributions. Min-max normalization is sensitive to outliers: one document with unusually high BM25 compresses all other BM25 scores near zero, making sparse contribution negligible. Z-score normalization produces negative values. No normalization approach is universally robust.

RRF is rank-based, so it is scale-invariant by construction. No normalization required. The k=60 smoothing constant diminishes the impact of very high ranks — preventing rank-1 from completely dominating the sum. Empirically, k=60 was found optimal across many web search benchmarks, though it can be tuned for specific domains.

Production default: always use RRF. Use linear combination only when you have labeled evaluation data and a calibration pipeline for alpha. RRF is zero-shot and consistently outperforms linear combination without tuning.
►How does HyDE work and what are its production failure modes?
Principal

Hypothetical Document Embedding (HyDE) addresses the semantic gap between short user queries (questions) and longer document passages (declarative statements). The LLM generates a hypothetical answer paragraph — a document that would answer the query if it existed. That hypothetical paragraph is embedded and used for retrieval instead of the original query embedding. A generated paragraph about the topic is semantically much closer to actual relevant documents than the brief question.

Failure mode 1 — Hallucinated hypothetical: If the LLM generates a plausible-sounding but factually wrong hypothetical, you embed and retrieve documents related to the wrong answer. This is particularly dangerous in technical and medical domains where LLM knowledge may be outdated or incorrect. You end up confidently retrieving documents that support a wrong premise.

Failure mode 2 — Domain specificity gap: For highly specialized queries about internal documents, proprietary processes, or very recent events, the LLM has no training signal to generate a good hypothetical. The generated text is generic, and retrieval quality falls below standard dense retrieval. HyDE is counterproductive when the LLM knows less than what is in the corpus.

Failure mode 3 — Latency violation: HyDE adds one full LLM call in the critical retrieval path — typically 200–800ms. For customer-facing systems with sub-second latency SLAs, this is often architecturally incompatible. HyDE belongs in research-grade or async retrieval contexts, not real-time customer support.

HyDE shines for: research assistants with no latency SLA, open-domain QA where LLM knowledge is well-calibrated to the corpus, and short ambiguous queries where query expansion adds measurable recall improvement.
§ 06 — HYBRID SEARCH

Hybrid Search Deep Dive — BM25, RRF & Score Fusion

The math behind BM25 and RRF is commonly tested at Principal+ level. Write the BM25 formula from memory and explain every parameter's role — this signals genuine depth beyond tutorial knowledge.

BM25 Formula — Complete Parameter Breakdown
BM25(Q, D) = sum_i[ IDF(qi) x f(qi,D) x (k1 + 1) /(f(qi,D) + k1 x (1 - b + b x |D|/avgdl)) ] IDF(qi) = log[ (N - n(qi) + 0.5) / (n(qi) + 0.5) + 1 ] Parameters: f(qi, D) = frequency of term qi in document D |D| = length of document D in tokens avgdl = average document length across the entire corpus N = total number of documents in corpus n(qi) = number of documents that contain term qi k1 = term saturation constant (default 1.2 to 2.0) b = length normalization constant (default 0.75)

k1 — term saturation: Controls how much additional occurrences of a term contribute to score. At k1=0, frequency doesn't matter at all. k1=1.2 is the BM25 default — a term appearing 3x in a doc scores about 2.1x a doc where it appears once (not 3x). This prevents term-stuffing. Raise k1 when repetition genuinely signals higher relevance (technical docs where repeated reference to a concept matters).

b — length normalization: At b=0, document length has zero effect — long documents are not penalized. At b=1, full normalization — a term appearing once in a short doc scores the same as appearing 10 times in a doc 10x longer. b=0.75 is the empirical optimum. Lower b for encyclopedic domains where longer documents genuinely contain more information worth rewarding.

Why BM25 beats TF-IDF: TF-IDF has no term saturation (frequency scales linearly — rewarding term stuffing) and no length normalization (longer docs score higher by default). BM25 fixes both, making it the modern baseline for sparse retrieval.

Interview Q&A — Hybrid Search
►What is SPLADE and when would you use it over standard BM25 in a hybrid system?
Architect

SPLADE (SParse Lexical and Expansion model) is a neural model that produces sparse vectors over the full vocabulary. Unlike BM25 which only scores terms literally present in a document, SPLADE learns to activate related vocabulary terms — a document about "myocardial infarction" gets high weights for "heart attack," "cardiac event," and "MI" even if those exact words never appear. This is vocabulary expansion via a learned neural model.

SPLADE produces a sparse vector of dimension V (vocabulary size, ~30,000 for BERT-based), where most entries are zero. This maps naturally to an inverted index — only non-zero dimensions need storage and scoring. Query-time latency is comparable to BM25; the additional cost is SPLADE inference at indexing time (one BERT-scale forward pass per document).

Use SPLADE over BM25 when: Your domain has significant vocabulary mismatch — users query in lay language, documents use technical language (or vice versa). Medical patient queries vs clinical documentation. Legal plain-English questions vs statute text. SPLADE bridges this gap with learned vocabulary expansion while maintaining sparse retrieval interpretability and inverted-index efficiency.

Use BM25 over SPLADE when: The domain is exact-match dominated (product codes, article numbers, IDs). Zero indexing latency is critical — BM25 requires no model inference. Infrastructure simplicity matters — BM25 runs in any search engine. SPLADE's expansion can introduce false positives when exact matching is the requirement.

In practice: SPLADE is most impactful in medical, legal, and scientific domains with strong vocabulary mismatch between query style and document style. For most enterprise FAQ and customer support applications, BM25 is sufficient and simpler to operate.

►When does hybrid retrieval fail to outperform pure dense retrieval?
Principal

Hybrid is not universally better than dense-only, and understanding the failure cases demonstrates real production experience:

1. Short chunks kill BM25 signal: BM25 requires sufficient term frequency and document length to compute meaningful IDF-weighted scores. Chunks of 50–100 tokens have insufficient text for BM25 to differentiate meaningfully between documents. In this regime BM25 adds noise to RRF fusion rather than signal, and hybrid degrades to slightly worse than pure dense. Minimum chunk size for BM25 contribution: ~150–200 tokens.

2. Fully semantic query domain: If all user queries are semantic paraphrases ("find something about strategic planning," "explain this concept") with no exact-term queries, BM25 contributes noise. A consumer app for fashion recommendations has no exact-match retrieval need — hybrid adds compute without quality improvement.

3. Vocabulary-uniform corpus: If all documents use nearly identical vocabulary (boilerplate legal contracts with the same clause structure), BM25 cannot discriminate between them — all documents score similarly on the same terms, producing uniform noise in the ranking.

4. RRF parameter mismatch: The default k=60 was empirically tuned for web search. For domain-specific retrieval where rank-position distributions differ significantly, k=60 may under-weight the superior retrieval system. Without tuning, the hybrid combination can underperform its best component.

Always measure hybrid vs dense-only on your evaluation set. Don't assume hybrid is always better. Measure Context Precision and NDCG@10 for both modes on your golden set before committing to hybrid infrastructure cost.
§ 07 — QUERY TRANSFORMATION

Query Transformation Techniques

A query arriving at your RAG system is almost never in optimal form for retrieval. Query transformation adds a layer between user intent and the retrieval call — improving recall at the cost of latency and LLM tokens.

🔀 Multi-Query
LLM generates N variations of the same query. Each retrieves top-k independently. Results deduplicated by chunk ID, merged, re-ranked. Best for recall improvement. Cost: N LLM calls in the retrieval path.
🔫 HyDE
LLM generates a hypothetical answer paragraph. That paragraph's embedding is used for retrieval instead of the query. Bridges the question-to-statement representation gap in embedding space.
↑ Step-Back Prompting
LLM abstracts the query to a higher-level principle. Retrieve for both the specific and abstract query. Captures foundational knowledge that contextualizes specific answers.
✂ Query Decomposition
LLM breaks a complex multi-part query into atomic sub-questions. Each sub-question retrieves independently. Answers synthesized. Required pattern for multi-hop RAG.
🌊 RAG-Fusion
Multi-query (3–5 variants) + RRF fusion on all result sets + citation-aware generation. Best quality, highest cost. Best for research assistants with no latency SLA.
📝 Query Rewriting
Fix grammar, resolve conversation coreferences, expand acronyms, add implicit context from history. Lightest-weight — often justified even under tight latency budgets using a small fast model.
Interview Q&A — Query Transformation
►How do you handle query transformation in a multi-turn conversational RAG system?
Principal

Multi-turn conversations introduce coreference that makes individual queries unintelligible to a retriever. "What were its consequences?" is meaningless to an embedding model without knowing the previous question was about a specific regulation or event. The canonical solution is standalone query generation before retrieval.

Implementation: Pass the last N turns of conversation (typically 3–5) plus the current query to a lightweight LLM with the prompt: "Rewrite the user's latest question as a complete, standalone query that requires no conversation history to understand. Resolve all pronouns, implicit references, and assumed context." The output is a fully specified query usable for retrieval independently. This can use a small, fast model (GPT-4o-mini, Claude-3-haiku) to minimize latency impact.

Conversation window management: Don't pass the full conversation history — it adds tokens and noise with diminishing signal value. Use the last 3–5 turns. For long conversations, maintain a rolling summary: a "context state" object updated after each turn that captures the key entities, topics, and decisions discussed so far. This summary replaces older turns in the rewriting context.

Multi-turn retrieval state: Advanced systems maintain a "retrieved context registry" — tracking which document chunks have already been retrieved and used across turns. LangGraph is well-suited: state stores conversation turns, used chunk IDs, and answer history explicitly. This prevents repeatedly retrieving the same chunks in a long conversation on the same topic, which both wastes tokens and can bias the LLM toward earlier retrieved content.

§ 08 — RE-RANKING

Re-ranking Systems

Re-ranking is the post-retrieval quality filter. It takes imprecise ANN candidates and scores them accurately — catching bi-encoder failures before they reach generation. The bi-encoder vs cross-encoder distinction is fundamental and frequently tested.

Bi-Encoder vs Cross-Encoder — Architectural Difference

Bi-encoder: Query and document encoded separately. Score = cosine(embed(Q), embed(D)). Documents pre-encoded and indexed offline. Query embedding computed once, dotted against all candidate vectors. O(1) per document at query time after indexing. Scales to millions of documents. Misses fine-grained query-document interactions because query tokens never attend to document tokens.

Cross-encoder: Query and document concatenated: [CLS] Q [SEP] D [SEP] → BERT → relevance score. Full bidirectional attention between query and document tokens. Cannot pre-encode documents — score depends on the specific (query, document) pair. O(k) inference for k candidates at query time. 100–1000x slower than bi-encoder but dramatically higher relevance quality.

Production pattern: Bi-encoder for first-stage retrieval (top-100 from millions, ~10ms). Cross-encoder for second-stage re-ranking (top-100 → top-10, ~200ms). Two-stage pipeline achieves cross-encoder quality at near-bi-encoder overall latency because the expensive cross-encoder only runs on a small candidate set.

Interview Q&A — Re-ranking
►How do you determine the optimal k for re-ranking, and how does it affect end-to-end system performance?
Principal

The re-ranking cutoff k is a latency-quality trade-off requiring empirical measurement on your specific system. Here is the three-step framework:

Step 1 — Measure recall@k from first-stage retrieval: For your golden evaluation set, plot the percentage of relevant documents appearing in the top-k of ANN retrieval across k=5, 10, 20, 50, 100. Find the elbow — the k where recall stops improving significantly. This is your minimum re-ranking k; you cannot re-rank what you did not retrieve.

Step 2 — Benchmark re-ranker latency vs k: Cross-encoder latency scales approximately linearly with k. Profile your specific re-ranker at k=20, 50, 100, 200. Cohere Rerank at k=50 is typically 150–300ms; at k=100 around 300–600ms. FlashRank on CPU at k=50 is 20–50ms; at k=100 is 40–100ms. Identify the maximum k that fits within your latency budget (re-rank latency must leave room for generation in your end-to-end SLA).

Step 3 — Measure quality improvement curve: From your re-ranked results, compare NDCG@5 and faithfulness when varying k_rerank from 20 to 100. Plot quality vs k_rerank. Find the plateau — above which adding more candidates to the re-ranker input yields no measurable quality improvement. This is your quality ceiling k.

Typical production values: k_retrieve = 20–50 from ANN; k_rerank to top-5 for generation. High-stakes systems: k_retrieve=100, rerank to top-10. Latency-critical consumer apps: k_retrieve=10, FlashRank only or RRF fusion without cross-encoder reranking.

§ 09 — GENERATION & PROMPTING

Generation Patterns & Prompt Engineering for RAG

Generation determines how retrieved context becomes an answer. Context management strategy, prompt design, and hallucination mitigation are architectural decisions with measurable quality impact.

Context Management Strategies Compared

Stuff: Concatenate all retrieved chunks into one prompt. Simple, fast, one LLM call. Fails when total context exceeds context window or when the lost-in-the-middle effect buries key information.

MapReduce: Map — process each chunk separately, produce a partial answer. Reduce — combine all partial answers into a final answer. Parallelizable (run all Map calls concurrently). Risk: partial answers may miss cross-chunk connections; reduces latency via parallelism but doubles LLM calls.

Refine: Iteratively refine a running answer with each new chunk. Sequential (cannot parallelize). Produces coherent, integrated answers that synthesize across chunks. Best for synthesis tasks requiring cross-chunk reasoning. Highest latency — k sequential LLM calls.

Lost-in-the-Middle: LLMs have primacy and recency bias — they attend more to content at the start and end of the context window. Performance follows a U-shaped curve: highest at position 1 and last position, lowest in the middle. Mitigation: place rank-1 chunk first, rank-2 chunk last, remaining chunks in the middle. Limit total chunks to 3–5 rather than stuffing 15+.

Interview Q&A — Generation
►How do you engineer a RAG system prompt to minimize hallucination while maximizing answer completeness?
Principal

The core tension: strict grounding instructions reduce hallucination but also reduce completeness — the LLM refuses to synthesize beyond what is literally stated. The goal is maximum faithfulness without excessive refusals.

Effective RAG system prompt structure:

  • Role and grounding instruction: "You are a [domain] assistant. Answer questions using ONLY the provided context passages. If the context does not contain sufficient information, say so explicitly rather than using your general knowledge."
  • Citation requirements: "When you make a factual claim, cite the source passage using [Source 1], [Source 2] notation. Every substantive claim must be traceable to a provided passage."
  • Uncertainty protocol: "If the context is ambiguous or if passages conflict, acknowledge this explicitly. Use hedging language: 'The context suggests...', 'Based on [Source 1]...' when certainty is incomplete."
  • Synthesis permission: "You may synthesize and connect information across multiple provided passages, but do not introduce information from outside the provided context."
  • No-answer protocol: "If the question cannot be answered from the provided context, respond: 'I do not have sufficient information in the provided documents to answer this question.' Do not attempt to answer from general knowledge."

What NOT to include: "Answer anyway if you are uncertain" — this is an explicit hallucination invitation. "Use your best judgment" — this opens the door to parametric knowledge injection. "Provide a comprehensive answer" — without grounding constraints, comprehensive means generating beyond context. Each of these phrases measurably increases faithfulness score drops in production monitoring.

►What is the lost-in-the-middle problem and what concrete production mitigations would you implement?
Senior

Research demonstrated that LLM performance degrades significantly when relevant information is positioned in the middle of a long context window, compared to the same information at the start or end — even with identical content. The performance curve is U-shaped. On 20-document multi-document QA tasks, accuracy at position 10 (middle) was measurably worse than position 1 (primacy) or position 20 (recency), by margins of 10–20% on standard benchmarks.

Concrete production mitigations:

Strategic chunk placement: Place the highest-relevance chunk (rank 1 from re-ranker) first in the context. Place rank-2 last. Place ranks 3–k in the middle. This exploits primacy and recency bias deliberately. Cost: zero. Implementation: sort chunks into [rank1, rank3, rank4...rankK, rank2] order before formatting the prompt.

Limit total context to 3–5 chunks: Fewer chunks means less "middle" exists. Counterintuitively, passing 5 high-quality chunks often produces better answers than 20 mediocre ones — less total noise for the LLM to navigate, less lost-in-the-middle surface area.

Chunk compression pre-generation: Summarize each retrieved chunk to its 1–2 most relevant sentences (using a small fast LLM) before including in the generation prompt. Smaller total context = less middle effect, and each chunk is already distilled to its key fact. Adds latency but improves faithfulness measurably in long-context scenarios.

Explicit section labeling: Label each chunk with its relevance rank: "MOST RELEVANT PASSAGE [Source 1]: ..." "SUPPORTING PASSAGE [Source 2]: ..." This helps the LLM explicitly locate and prioritize sections rather than scanning a homogeneous context block.

Interview Q&A — Evaluation
►How do you build a golden evaluation dataset for production RAG and what makes a good golden set?
Principal

A golden evaluation set is the bedrock of RAG quality assurance. A poor golden set gives false confidence; a well-constructed one catches regression early and guides optimization precisely.

The unit of a golden set: (query, ground-truth answer, relevant document chunks). This triple is what every RAGAS metric requires. Context Recall and Context Precision need the relevant chunks. Answer Correctness needs the ground-truth answer. You need all three components per example.

Query diversity requirements: A golden set that only tests easy queries is useless for finding failure modes. Target: 30% easy (direct factual lookup), 40% medium (requires synthesis across 2–3 chunks), 30% hard (multi-hop reasoning, edge cases, "not covered" scenarios where the answer is that information is absent). The hard and negative examples (queries where no good answer exists in the corpus) are often the most valuable for catching hallucination.

Practical generation pipeline: (1) Use GPT-4 to generate question-answer pairs from your corpus at scale (Evol-instruct style, instructing diverse difficulty levels). Budget 50K–500K synthetic pairs for regression testing. (2) Human SMEs review and correct 100–500 of these pairs for high-confidence evaluation. (3) Use the human-corrected set for primary quality decisions; synthetic set for regression testing on every deployment. (4) Continuously expand from production failure cases — queries flagged by low faithfulness scores or user thumbs-down.

In practice, 150 well-curated human-annotated evaluation examples reveal most retrieval and generation failure patterns. Beyond 500 queries, marginal diagnostic value drops significantly unless you are covering highly diverse document types or query categories.
►Faithfulness is high but Answer Relevancy is low. What does this diagnose and how do you fix it?
Principal

This specific RAGAS metric signature is highly diagnostic. High faithfulness means everything stated in the answer is grounded in the retrieved context — no hallucination. Low answer relevancy means the answer does not actually address the user's question despite being grounded.

The root cause is almost always a retrieval-query intent mismatch. The retrieval system returned documents related to some aspect of the query vocabulary, but not the core intent of the question. The LLM then faithfully generates an answer from those documents — which is topically adjacent but not on-point.

Example: Query: "What are my passenger rights if my flight is cancelled?" System retrieves chunks about delay compensation (similar vocabulary: "flight," "compensation," "passengers"). LLM generates a faithful, well-grounded answer about delay rights. But the user asked about cancellation. Faithfulness = 1.0 (everything said is in context). Answer Relevancy = 0.4 (wrong topic).

Diagnosis workflow: (1) Inspect retrieved chunks for this query type — are the relevant chunks being retrieved at all? (2) If yes but ranked low, fix re-ranking. (3) If no, fix chunking (document-aware chunking may separate "cancellation" and "delay" policies into different sections that are interleaved in the retrieval), or fix the embedding model (dense may conflate "delay" and "cancellation" semantically). (4) If the chunks are retrieved but the answer still misses — the generation prompt may not be focusing the LLM on what the user specifically asked. Add explicit instructions to stay on the specific question asked.

►How do you implement LLM-as-judge for faithfulness evaluation and what are its known biases?
Architect

LLM-as-judge is the de facto standard for scalable reference-free evaluation. For faithfulness, the implementation follows NLI principles in two steps:

Step 1 — Claim extraction: Prompt GPT-4: "Extract all distinct factual claims from this answer as separate bullet points. Each bullet should be one atomic claim. Answer: [answer]." This produces a list of 3–15 claims depending on answer length.

Step 2 — Claim verification: For each extracted claim, prompt: "Based ONLY on this context passage: [retrieved context]. Is this claim: (A) Fully supported by the context, (B) Partially supported, (C) Not supported, or (D) Contradicted by the context? Claim: [claim]. Answer with only A, B, C, or D." Faithfulness score = count(A) / total_claims. Weight B at 0.5 if desired.

Known biases — must disclose in an interview:

  • Length bias: LLM judges tend to rate longer, more detailed answers as higher quality even when shorter answers are more faithful. Explicitly instruct the judge to evaluate accuracy and groundedness, not thoroughness.
  • Position bias: When comparing answer A vs answer B in a pairwise setup, judges favor whichever is presented first (primacy effect). Always evaluate independently, never comparatively, for faithfulness scoring.
  • Self-enhancement bias: GPT-4 judging GPT-4 outputs is more lenient than Claude judging GPT-4. Use a different model family as judge when possible — cross-family evaluation is more objective.
  • Verbosity inflation: The judge may credit statements as "supported" if they sound plausible given the context, even when not explicitly present. Mitigate with explicit instruction: "Judge ONLY based on the provided text. Your general knowledge must not influence this evaluation."
§ 11 — AGENTIC RAG

Agentic RAG Patterns

Agentic RAG gives the LLM control over the retrieval process itself. Instead of a fixed pipeline, the model decides when to retrieve, what to retrieve, and whether to trust the result. This is the frontier of production RAG architecture in 2025–2026.

🔄 Self-RAG
Trained model generates special tokens: [Retrieve] when knowledge needed, [ISREL] to judge retrieved doc relevance, [ISSUP] to check answer-doc support, [ISUSE] to rate answer utility. Enables on-demand per-sentence retrieval. Requires fine-tuning — cannot be added via prompting to GPT-4.
🔧 Corrective RAG (CRAG)
Retrieval evaluator scores document quality on 0–1. If score above threshold: proceed to generation. If in middle band: filter + web search augmentation. If below threshold: web search replaces RAG entirely. Handles out-of-corpus queries gracefully. Web search adds latency when triggered.
🗺️ Adaptive RAG
Query complexity classifier routes to: (1) direct answer with no retrieval, (2) single-hop standard RAG, (3) multi-hop RAG with decomposition, (4) web search for current events. Reduces average latency by skipping retrieval for simple queries. Requires a trained or prompted classifier.
📊 LangGraph Multi-Agent
State machine: Router → Retriever → Doc Grader → Query Rewriter → Generator → Hallucination Checker → Answer Grader. Supports cycles on failure, parallel subgraphs, and explicit state management. Each node is a Python function; edges are conditional routing logic.

Interview Q&A — Agentic RAG
►What is Self-RAG and how does it fundamentally differ from standard RAG?
Architect

Standard RAG is a deterministic pipeline: every query triggers retrieval, every retrieved context goes to generation, regardless of whether retrieval was needed or whether the retrieved docs are relevant. Self-RAG trains the LLM end-to-end to make these decisions dynamically during the generation process itself.

Self-RAG introduces four special token types baked into the model vocabulary: [Retrieve] generated when the model determines it needs external information for the next sentence. [ISREL=yes/no] generated after reading a retrieved passage to judge its relevance. [ISSUP=yes/partial/no] generated after producing a statement to verify the retrieved passage supports it. [ISUSE=1-5] utility score for the overall generated answer.

This enables sentence-level adaptive retrieval: the model retrieves when generating a factual claim requiring external grounding, but does not retrieve when generating a transition sentence, conclusion, or something within its parametric knowledge. It self-critiques mid-generation. At inference time, you can decode multiple candidate responses (with and without retrieval for each sentence) and select the highest ISUSE-scored output.

Key difference: Standard RAG always retrieves, even when the LLM parametric knowledge is sufficient — adding latency and context noise unnecessarily. Self-RAG retrieves on-demand and self-validates each retrieved document for relevance. In the original paper, Self-RAG outperforms retrieval-always RAG on multiple benchmarks while being faster on queries that do not require external knowledge.

Production limitation: Self-RAG requires fine-tuning. You cannot bolt it onto GPT-4 or Claude via prompting alone. The training data requirement (generating the special tokens) is non-trivial. Most production systems in 2025–2026 use prompt-based query routing (Adaptive RAG) rather than Self-RAG because of the fine-tuning overhead and the availability of capable frontier models that make routing via prompting sufficient.

►How do you prevent infinite loops in a LangGraph agentic RAG system?
Architect

Infinite loops in agentic RAG occur when an agent cycles between failing states without a termination condition. Classic scenario: Retriever → DocGrader (fails: docs not relevant) → QueryRewriter → Retriever (still fails) → QueryRewriter → forever.

Prevention mechanism 1 — Explicit retry counter in state: Include retry_count: int = 0 in the LangGraph state schema. Every retrieval retry increments this counter. Every conditional edge that routes back to Retriever first checks: if state.retry_count >= MAX_RETRIES (3): route to END_graceful else: route to retrieve. This guarantees termination on any single failing path.

Prevention mechanism 2 — Visited query tracking: Store hashed versions of all query variants tried in tried_queries: List[str]. If QueryRewriter generates a query too similar (cosine similarity above 0.95) to a previously tried query, force a different path — web search fallback or graceful degradation rather than another retrieval retry.

Prevention mechanism 3 — LangGraph recursion limit: LangGraph has a built-in recursion_limit config parameter. Set it as a hard ceiling: graph.invoke(inputs, config={"recursion_limit": 15}). This catches any loop that slips through conditional logic. The graph raises a RecursionError after 15 total steps regardless of path — your application code catches this and returns a graceful no-answer response.

Design principle: Model every agentic graph as a finite state machine with provable termination. For every cycle in the graph, there must exist a counter, condition, or visited-set check that guarantees the cycle terminates. Infinite cycles are a design error, not a runtime error to catch and ignore.

►How do you detect RAG quality degradation in production before users notice?
Principal

RAG quality degradation manifests differently at different layers, each with a distinct early warning signal:

Embedding distribution drift (index staleness): As new documents are added and old ones updated, the distribution of embedding vectors in your index shifts. Monitor this with Population Stability Index (PSI) on a random sample of query embeddings weekly. PSI above 0.2 indicates significant distribution shift — often caused by corpus changes that make your embedding model less appropriate for the current document population. Kolmogorov-Smirnov test on embedding coordinate distributions can also catch this without labeled data.

Retrieval precision signals: Track zero-result rate — queries where top-1 chunk cosine similarity falls below a threshold (e.g., 0.60). Track the distribution of top-1 similarity scores weekly. A downward shift indicates growing corpus-query mismatch. Alert at two standard deviations below the 30-day rolling mean.

Faithfulness sampling: Run LLM-as-judge faithfulness evaluation on 5–10% of production queries (randomly sampled, not all queries). Compute a rolling 7-day faithfulness score. Alert if it drops more than 0.05 from the 30-day baseline. This catches generation-side degradation from model updates, prompt drift, or context window changes.

Implicit user signals: Track user thumbs-down rate, re-ask rate (user immediately asks the same question again in different words), and answer acceptance rate (did the user act on the answer or continue searching). These are lagging indicators but high signal for systematic quality issues.

Proactive golden set regression: Run your golden evaluation set against production on every deployment and weekly on a schedule. A greater than 3% drop in any RAGAS metric triggers a deployment rollback or an alert requiring investigation before the next release.

►How would you reduce RAG end-to-end latency from 3 seconds to under 800ms without sacrificing quality?
Architect

This is a systems engineering optimization problem that requires profiling before optimizing. Here is the systematic approach:

Step 1 — Profile with LangSmith or custom instrumentation: Measure P95 latency per stage. Typical breakdown for a 3s system: query embedding 50ms, ANN retrieval 100ms, re-ranking 400ms, generation 2,200ms, overhead 250ms. Always find the dominant term before optimizing.

If generation dominates (most common case): Enable streaming generation — users perceive 300ms to first token as fast even if total generation is 2s. Switch to a smaller LLM for simpler queries via routing: GPT-4o-mini (5x faster than GPT-4o for straightforward Q&A). Reduce context size — pass top-3 chunks instead of top-10. Each additional chunk adds ~100–200ms to generation. Evaluate whether quality holds on your golden set.

If re-ranking dominates: Switch from Cohere Rerank (300–500ms at k=50) to FlashRank (20–50ms). Reduce k_rerank from 50 to 20 — measure quality impact on your golden set. For most applications, quality difference between k=20 and k=50 re-ranking is under 2% NDCG. Use RRF-only fusion for lower-stakes query types, saving the cross-encoder for high-confidence or HITL-flagged queries.

If retrieval dominates: Run dense and sparse retrieval in parallel (async/concurrent, not sequential). Tune HNSW ef parameter down from 200 to 50 — 3x faster query with roughly 1% recall degradation. If payload filtering is degrading ANN, pre-partition the index by high-selectivity attributes (user ID, document type) into separate namespaces.

Cross-cutting optimization — semantic caching: If 20–30% of queries are semantically similar (FAQ-type patterns), semantic caching reduces average latency by that percentage at no quality cost. A 20% cache hit rate at sub-10ms cache latency saves roughly 600ms on average for a 3s system, contributing significantly toward the 800ms target.

Anti-Patterns — Incompatible Combinations That Kill RAG Quality:

Parent-child chunking + pure BM25 retrieval: BM25 term frequencies are computed on child text, but you return parent text. ►Your company wants to build a RAG system over internal Slack/email/documents. What are the unique challenges versus standard document RAG, and how do you address them?
Architect

Unstructured conversational data (Slack, email) presents fundamentally different challenges from document RAG:

Challenge 1 — Content quality and noise: Slack messages are full of informal language, emoji, abbreviations, context-dependent jokes, and partial sentences. Embeddings of "lol yeah let's do that tomorrow" are meaningless as standalone retrieval units. Solution: conversation-thread-aware chunking — group Slack messages by thread (not individually), treat a thread as a semantic unit. Filter out low-content messages (under 20 words) and bot messages at indexing time. Email: include subject line + relevant reply chain as the chunk, not individual emails.

Challenge 2 — Access control complexity: Slack channels and DMs have per-user/per-channel permissions. A query from user A should NEVER retrieve messages from a channel user A is not a member of. Standard metadata filtering is insufficient — you need permission graph evaluation at query time. Solution: at indexing, store channel_id and allowed_user_ids as metadata per chunk. At query time, filter on allowed_user_ids contains [current_user_id]. This requires syncing Slack membership data into your vector DB metadata on a schedule.

Challenge 3 — Temporal decay: A Slack message from 3 years ago about a system architecture decision is lower value than one from last week, but may still be relevant for historical decisions. Solution: implement time-decay scoring — apply a decay factor to the similarity score based on message age: effective_score = cosine_score * (0.7 + 0.3 * recency_weight) where recency_weight decays from 1.0 (today) to 0.0 (more than 2 years old). Make the decay rate configurable per search context.

Challenge 4 — PII and sensitive data: Emails and Slack contain salaries, performance reviews, personal information, and confidential negotiations. RAG cannot indiscriminately index all of this. Solution: PII detection (Presidio or AWS Comprehend) at ingestion time — flag or redact PII before embedding. Certain channels (HR channels, legal holds) are excluded from the index entirely. Require explicit opt-in from content owners for sensitive channels.

Challenge 5 — Disambiguation: "What did we decide about the API?" is ambiguous — which API, when, in what context? Conversational data has heavy implicit context. Solution: require date ranges in queries (enforce a time filter selector in the UI), enable multi-turn clarification, and always surface the source messages prominently so users can validate context themselves.

►Your RAG system has high faithfulness (0.91) but users are still complaining the answers are wrong. What is happening and how do you investigate?
Architect

This is a classic case where faithfulness is measuring the wrong thing. High faithfulness means answers are grounded in retrieved context — but it says nothing about whether the retrieved context was correct. The retrieved context itself may be wrong, outdated, or not the authoritative source.

Root cause investigation checklist:

1. Index staleness: Are the retrieved documents up to date? If a policy changed last month and the old version is still in the vector index (because the update pipeline failed or was slow), the LLM faithfully answers from stale data. Check index freshness lag metrics. Audit recently changed source documents against their indexed versions.

2. Wrong document retrieved (not wrong answer): The retrieved chunk is factually correct in isolation but is the wrong section for the query. Example: user asks about "cancellation policy effective January 2024" but retrieves a chunk from the 2022 version. Faithfulness = 1.0 (grounded in that chunk) but the answer is wrong because the 2022 policy is outdated. Fix: add document version/date metadata and enforce recency filtering where applicable.

3. Faithfulness measures claim support, not claim completeness: A 10-word answer grounded in one claim can score 1.0 faithfulness while missing the three other claims that would make the answer actually useful and correct. Measure answer correctness (requires ground truth), not just faithfulness. High faithfulness + low answer correctness = correct-but-incomplete retrieval.

4. Context Recall measurement gap: Check Context Recall on your golden set. If Context Recall is below 0.75, relevant information is not being retrieved at all — the answer is generated from an incomplete context, producing technically faithful but factually wrong answers because the full picture was never available to the LLM.

Key insight for interviews: faithfulness is a necessary but not sufficient condition for answer quality. High faithfulness rules out hallucination but not stale data, wrong document selection, or incomplete retrieval. Always evaluate all 7 RAGAS metrics, not just faithfulness.
►How would you design a multi-tenant RAG system where 500 enterprise clients each have their own document corpus, with strict data isolation guarantees?
Architect

Multi-tenant RAG isolation is an architecture-first problem — data isolation cannot be bolted on after the fact. Two fundamental patterns exist, each with distinct trade-offs:

Pattern 1 — Shared index with tenant filtering (recommended for 99% of use cases): All tenants share one vector index. Every chunk has a tenant_id metadata field. Every query has a mandatory tenant_id filter applied before ANN search. This requires a vector DB with efficient payload filtering (Qdrant, Weaviate, Pinecone namespaces). Pros: operationally simple — one index to manage, one embedding model, shared infrastructure cost. Cons: filter selectivity problem at low tenant document counts (post-filter degrades when a tenant has only 100 documents in a 10M-vector index).

Pattern 2 — Dedicated index per tenant (for large tenants or strict isolation SLAs): Each large tenant gets a dedicated vector index (or Pinecone namespace, or Weaviate collection). Smaller tenants share a pooled index. Pros: no cross-tenant data co-mingling even at the infrastructure level — satisfies the strictest enterprise security requirements. Cons: operational complexity scales with tenant count; cannot share ANN index cache across tenants.

Hybrid approach (production best practice): Tier tenants by size and security requirements. Top 10% of tenants by document volume or paying for enterprise isolation tier → dedicated index. Bottom 90% → shared index with tenant_id filtering. This reduces operational complexity while satisfying enterprise customers' isolation needs.

Critical implementation requirements: Tenant ID must be immutable metadata attached at indexing time — not derivable from document content. Implement a query interception layer that always injects the tenant_id filter, making it impossible for application bugs to issue cross-tenant queries. Audit log every query with tenant_id for compliance. Implement data deletion pipeline: when a tenant churns, purge all their chunks from the index (requires document_id → chunk_id mapping for bulk delete). Regular isolation penetration testing — confirm that tenant A cannot retrieve tenant B's documents under any query path.

►Walk me through how you would evaluate two competing embedding models to decide which to use in production for your RAG system.
Architect

Embedding model evaluation for RAG production is a four-stage process: offline retrieval quality, cost modeling, latency profiling, and production shadowing.

Stage 1 — Offline retrieval quality: Build a golden evaluation set with (query, relevant_chunk_ids) pairs (100–500 examples covering diverse query types). Re-index your production corpus with both models. Measure NDCG@10, Recall@10, and MRR for both models on this set. Run this evaluation with: (a) dense-only retrieval, (b) hybrid with BM25. A model that improves dense retrieval by 5% NDCG is significant. Sub-1% differences are within noise — don't change models for less than 3% improvement.

Stage 2 — Cost modeling: Calculate total cost of ownership: (a) indexing cost — price per 1M tokens for embedding your entire corpus plus re-indexing frequency. (b) query cost — price per 1M tokens for embedding incoming queries at your QPS. For self-hosted models: GPU compute cost per hour / queries per hour. For API models: token price x average query length x daily volume. Build a 12-month cost model. A self-hosted model might cost $2K/month in GPU but save $8K/month in API fees at high volume.

Stage 3 — Latency profiling: Measure P50/P95/P99 embedding latency under production-level load (not just single-request benchmarks). API models have network latency variability. Self-hosted models have cold-start issues and require GPU warm-up. Simulate your peak QPS in a load test. Ensure the embedding step does not become a latency bottleneck under load.

Stage 4 — Production shadowing: Before full rollout, shadow the new model alongside the existing one in production. For 5% of production queries: run both models, log both retrieval results, measure implicit user feedback (did the user accept the answer or re-ask?). After 2–4 weeks of shadow data, compare user acceptance rates between models. Real user behavior is the gold standard for model selection, not offline benchmarks alone.

Decision rule: require a statistically significant improvement in BOTH offline NDCG and online user acceptance rate before switching production models. The re-indexing cost and engineering risk of a model migration must be justified by demonstrated quality improvement, not just benchmark numbers.
►How do you handle a production RAG system where the LLM API has a 30-second outage? What is your resilience architecture?
Architect

LLM API resilience requires a layered fallback strategy — a single point of dependency on one LLM provider is an architectural vulnerability. Design for degraded-but-functional service during outages, not complete failure.

Layer 1 — Multi-provider primary/secondary: Configure both a primary LLM (GPT-4o) and a hot standby (Claude Sonnet or Gemini Pro) with identical system prompts and token budgets. Use a circuit breaker pattern: if the primary returns 5xx errors or exceeds 5s timeout for 3 consecutive requests, automatically route all traffic to the secondary for 2 minutes, then retry primary. LangChain and LiteLLM both support fallback provider configuration natively.

Layer 2 — Semantic cache as warm fallback: A semantic cache (GPTCache, Momento) returns cached responses for similar queries instantly, completely bypassing the LLM. During an outage, cache hit rate becomes your availability floor. Increase the cache cosine threshold from 0.92 to 0.85 during outage mode — accept slightly less precise cache matches to serve more queries from cache. This alone can serve 20–40% of queries during a brief outage.

Layer 3 — Retrieval-only degraded mode: If all LLM providers are down (rare but possible during major infrastructure events), serve retrieval-only results: return the top-3 raw retrieved chunks with their source documents highlighted. No LLM synthesis — just the source passages. This satisfies many queries (the user needed to find the document, not necessarily a synthesized answer) and keeps the system functional at degraded quality.

Layer 4 — Async queue for generation: For non-real-time use cases (report generation, batch analysis), queue generation requests during outage periods and process them when the primary LLM recovers. Users receive a "Your request is being processed" response immediately and a notification when the result is ready.

Observability: Monitor LLM API error rates with a separate synthetic canary — a test query that runs every 60 seconds and alerts within 90 seconds of provider degradation. This gives you warning before end users experience failures, enabling proactive fallback routing rather than reactive recovery.

►A new engineer joins your team and asks: "Should we switch from our current RAG system to a GraphRAG approach?" How do you evaluate this?
Architect

GraphRAG (Microsoft's approach, published 2024) builds a knowledge graph from the document corpus — extracting entities and relationships — and uses community detection to identify thematic clusters. Queries retrieve relevant graph communities plus specific entity subgraphs rather than flat chunks. This enables answers that synthesize across many documents at a theme level, not just locally relevant chunks.

When GraphRAG is worth the complexity: The canonical use case is queries that require understanding the full scope of a topic across an entire corpus — "What are all the themes and stakeholder relationships in these 10,000 meeting transcripts?" Standard RAG retrieves at most top-k locally relevant chunks; GraphRAG can surface corpus-wide patterns. Also valuable for: relationship queries ("How is entity A connected to entity B across documents?"), trend analysis across large corpora, and knowledge synthesis tasks.

GraphRAG's costs (which the engineer must understand before switching): (1) Indexing cost is dramatically higher — entity extraction and relationship building requires LLM calls per document chunk, making indexing 10–100x more expensive than standard RAG. For a 1M document corpus, GraphRAG indexing can cost thousands of dollars in LLM API fees. (2) Index rebuild time — any document update requires rebuilding affected community summaries, not just re-embedding one chunk. Update latency goes from seconds (standard RAG upsert) to hours (GraphRAG community rebuild). (3) Query latency — graph traversal plus community summary retrieval adds meaningful overhead. (4) Operational complexity — knowledge graph maintenance, community drift, entity deduplication are non-trivial ongoing engineering problems.

My evaluation framework for the team: Measure what percentage of your current user queries are corpus-wide synthesis queries (GraphRAG's strength) versus targeted fact lookup or specific document queries (standard RAG's strength). If under 10% of queries are corpus-wide synthesis, GraphRAG's overhead is not justified. Run an A/B comparison on your hardest synthesis queries with a prototype before committing to full migration. GraphRAG is a powerful tool for specific use cases — it is not a general replacement for standard RAG.

►How do you approach cost optimization for a RAG system that is costing $50K/month in LLM API fees and needs to be reduced to $20K?
Architect

A 60% cost reduction is achievable without quality degradation if you apply optimizations systematically. Start with instrumentation — you cannot optimize what you have not measured.

Step 1 — Cost attribution (first week): Break down the $50K by cost component: embedding API calls (query + indexing), generation API calls (model tier x tokens), re-ranking API calls, and any agent/query transformation LLM calls. Typically, generation dominates at 70–80% of total cost. Identify the top 20% of query types by token consumption — these are the targets.

Step 2 — Semantic caching (saves 15–30%): Implement semantic caching on query embeddings. At a cosine threshold of 0.92, a 20–30% cache hit rate is achievable for most FAQ-heavy applications. On a $50K baseline, this alone saves $10–15K/month at zero quality cost. This should be the first optimization deployed — fastest ROI, zero quality risk.

Step 3 — Query routing to smaller models (saves 20–35%): Classify queries by complexity. Simple lookup queries ("what is the return policy?") can use GPT-4o-mini at 5x lower cost than GPT-4o with equivalent quality. Instrument your current system — label the last 1,000 queries as simple/medium/complex using GPT-4o itself. If 40% are simple, routing them to GPT-4o-mini saves 40% x 80% of generation cost (mini is ~80% cheaper). Validate quality on a holdout set before full rollout.

Step 4 — Context window reduction (saves 10–20%): Reduce from stuffing top-10 chunks to top-3 or top-5. Measure faithfulness and answer correctness impact on your golden set. Most systems see under 3% quality degradation from top-10 to top-5 while reducing input tokens by 40–50%. At $50K baseline with generation dominating, this saves $5–10K/month.

Step 5 — Embedding model downgrade (saves 5–10%): Switch from text-embedding-3-large to text-embedding-3-small for query embedding (indexing is one-time). 50% cost reduction on query embedding with typically 1–3% NDCG degradation. Validate on your golden set that retrieval quality is maintained before switching production.

Combined savings: Caching (20%) + routing (25%) + context reduction (15%) + embedding downgrade (5%) = ~65% cost reduction on the $50K baseline, bringing to ~$17.5K/month — under the $20K target with margin for quality monitoring overhead. Each optimization should be deployed and validated independently before stacking.

►How do you measure and improve the "correctness" of a RAG system when you do not have ground-truth labels for most queries?
Architect

This is the fundamental challenge of production RAG evaluation — you typically have labels for 200–500 golden set queries but face millions of unlabeled production queries. Three approaches address this at different fidelity levels:

Reference-free proxy metrics (scalable, lower fidelity): Faithfulness (LLM-as-judge on sampled production queries, 5–10% sample rate) measures hallucination without ground truth. Answer Relevancy (reverse-question cosine similarity) measures on-topicness without ground truth. These are production monitoring metrics — they catch degradation without requiring labels. Alert threshold: 2-sigma drop from 30-day baseline.

Implicit feedback as correctness proxy (scalable, medium fidelity): In task-completion applications, user behavior signals correctness. Did the user accept the generated answer and proceed with the task? Did they immediately re-ask the same question in different words? Did they escalate to a human agent? Track these signals per query type. A query with a 70% re-ask rate has a systematic correctness problem, even without explicit labeling. This is your highest-signal production metric for correctness.

LLM-generated pseudo-labels (scalable, medium-high fidelity): Use GPT-4 to generate ground-truth answers for the top 1,000 highest-volume production query types. This is expensive ($50–200 one-time) but creates a labeled evaluation set covering your actual production distribution. Re-evaluate your system against these pseudo-labels monthly. The pseudo-labels themselves may not be perfectly correct, but they provide a consistent comparison baseline for detecting regression.

Targeted human annotation of failure clusters (low volume, highest fidelity): Use embedding clustering to find clusters of similar queries. Sample 5 queries from each cluster. Identify clusters with low user acceptance rates. Send these 50–100 queries to human annotators for ground-truth labeling. This focuses expensive human annotation on the highest-impact areas — failure clusters — rather than random queries, maximizing annotation ROI.

The practical answer: production correctness measurement is a portfolio of signals at different fidelity and cost levels. No single metric is sufficient. High-frequency low-fidelity metrics (faithfulness sampling, user acceptance rate) provide early warning. Low-frequency high-fidelity metrics (golden set evaluation, targeted human annotation) provide deep diagnosis.
►Explain the RAG "needle in a haystack" problem. What causes it and how do you architect around it?
Architect

The needle-in-a-haystack problem in RAG refers to retrieval failure when the relevant information is a single specific fact buried in a large corpus — and the query phrasing is insufficiently similar to the chunk containing that fact for ANN search to rank it highly.

Root causes: (1) Vocabulary mismatch — the query uses different terminology than the relevant chunk. Dense embeddings can bridge this but imperfectly for very domain-specific terms. (2) Single-sentence facts — a one-sentence policy exception buried in page 47 of a 200-page document produces a chunk embedding dominated by surrounding context rather than the specific exception. The embedding is "diluted" by non-relevant context. (3) Popularity bias in embeddings — frequently discussed topics have richer embedding representations; rare facts have weaker retrieval signal.

Architectural mitigations:

Smaller chunks with parent-child: Smaller child chunks (64–128 tokens) produce embeddings more tightly focused on the specific fact. A 64-token chunk containing one key exception produces an embedding that is that exception, not a diluted representation. Parent-child then returns sufficient context for generation. This is the highest-impact mitigation for needle retrieval.

Hybrid retrieval with BM25: If the query contains any distinctive keyword also present in the needle chunk, BM25 will rank it highly even if dense misses it. Hybrid RRF catches needles that dense misses if they contain distinctive terminology.

Multi-query retrieval: Generate 3–5 query variants covering different ways to phrase the question. One variant may use the exact terminology that matches the needle chunk even when the original phrasing misses it.

Sparse keyword boosting: For known "high-value needle" facts (critical safety clauses, key exceptions, specific policy numbers), index them separately with keyword metadata tags. If a query pattern matches a known needle type, apply a metadata boost to surface those specific chunks higher in ranking.

SPLADE or learned sparse models: SPLADE's vocabulary expansion helps when the needle chunk uses terminology not in the query. The model learns to represent related vocabulary in the sparse space, bridging the terminology gap that causes dense retrieval to miss.

Topic 02

Chunking strategy

Why I chose it: Chunking is the first major quality gate. If the evidence is split incorrectly, no vector database or LLM can fully recover. It demonstrates that I understand document structure, retrieval granularity, and context assembly.
Interview phrasing: "I chose chunking because it converts business knowledge into retrievable units. For policies I may use parent-child chunks; for code I preserve functions; for manuals I use heading-aware chunks. The choice depends on query granularity and source structure."

Topic 03

Embedding models

Why I chose it: Embeddings define the semantic search space. This topic shows that I can compare dense, sparse, multilingual, domain-tuned, and multi-vector approaches instead of treating embeddings as a commodity API call.
Interview phrasing: "I chose embeddings because the model determines what similarity means. A legal corpus, multilingual support portal, and code assistant may require different embedding strategies and an offline bake-off against representative queries."

Topic 04

Vector database selection

Why I chose it: The vector store is an architectural commitment with implications for scale, tenancy, filtering, governance, operational burden, and cost. This is where an Architect must justify managed versus self-hosted trade-offs.
Interview phrasing: "I chose vector database selection because the right answer depends on scale and platform constraints. pgvector may be enough for a small internal app; Qdrant or Milvus may fit large self-hosted workloads; managed services may win when team velocity matters."

Topic 05

Retrieval strategies

Why I chose it: Retrieval is the core recall layer. Principal-level candidates must know that pure dense retrieval is not always enough, especially for exact IDs, product codes, error messages, legal clauses, and names.
Interview phrasing: "I included retrieval strategies because different query classes need different retrievers. Semantic questions benefit from dense retrieval, exact terms benefit from sparse retrieval, and enterprise search usually needs hybrid retrieval with metadata filters."

  • Query class
  • Coverage
Topic 06

Hybrid search and fusion

Why I chose it: Hybrid search is one of the most practical production improvements because it combines semantic recall with lexical precision. It demonstrates a mature approach to enterprise data where vocabulary and identifiers matter.
Interview phrasing: "I chose hybrid search because enterprise users rarely ask only semantic questions. They ask for policy numbers, ticket IDs, acronyms, and exact product names. Fusion methods like RRF let me combine signals without over-trusting one score scale."
  • Lexical match
  • Semantic match
  • Fusion quality
Topic 07

Query transformation

Why I chose it: User questions are often incomplete, conversational, ambiguous, or vocabulary-mismatched against the corpus. Query rewriting, decomposition, HyDE, and multi-query retrieval improve recall before the ranking stage.
Interview phrasing: "I chose query transformation because production users do not write perfect search queries. For follow-up questions, I need conversation-aware rewriting; for broad questions, I may decompose; for terminology mismatch, I may use multi-query expansion."
  • Rewrite quality
  • Recall lift
  • Added latency
Topic 08

Re-ranking

Why I chose it: Re-ranking is the precision layer that turns a broad candidate set into a high-quality context window. It is essential when the generator can only see a few chunks and mistakes are expensive.
Interview phrasing: "I chose reranking because retrieval and generation have different needs. Retrieval should cast a wide net; reranking should decide which evidence deserves the limited prompt budget."
  • Precision@k
  • Context budget
  • Latency budget
Topic 09

Generation and prompt design

Why I chose it: Even perfect retrieval can fail if the generator is not constrained to use evidence, cite sources, handle uncertainty, and produce the format required by the product. This topic connects retrieval architecture to user experience.
Interview phrasing: "I chose generation because the LLM is the final policy enforcement point. It must answer from retrieved context, cite evidence, refuse unsupported claims, and use structured output when downstream systems consume the response."
  • Faithfulness
  • Citation coverage
  • Format validity
Topic 10

Evaluation and RAGAS-style metrics

Why I chose it: Evaluation separates senior experimentation from principal ownership. Without golden datasets, regression tests, and production feedback loops, quality becomes subjective and every stack change is risky.
Interview phrasing: "I chose evaluation because the architecture is only defensible if we can measure it. I would track retrieval recall, context precision, answer faithfulness, answer relevance, latency, cost, and no-answer correctness by query class."

  • Regression gate
  • Quality SLO
Topic 11

Agentic RAG

Why I chose it: Agentic RAG matters when simple retrieve-generate is not enough: routing, planning, tool use, query repair, document grading, and answer validation are needed. It also shows that I know when agentic complexity is justified.
Interview phrasing: "I chose Agentic RAG because some workflows require decisions, retries, and tools. But I would not start there by default; I would introduce agents only when measured failure modes justify the added latency, cost, and observability burden."

Topic 12

MLOps and production operations

Why I chose it: Production RAG is a distributed system, not a notebook. This topic covers ingestion pipelines, index freshness, monitoring, drift, access control, incident response, cost controls, and deployment safety.
Interview phrasing: "I chose MLOps because most RAG failures happen after the demo: stale indexes, broken connectors, missing ACLs, cost spikes, and silent quality regressions. An Architect must design for ownership and operability."
